Architectural Evolution

The Story & Purpose

Why we decoupled optional UI features from component blueprints and built a pure declarative instruction runner.

The Imperative UI Trap

In web application development, tables and list views rarely exist in isolation. Users almost always demand:

  • A Search Bar to filter items on the fly
  • A Serial Number (#) column to track row positions
  • An Actions Column with edit, view, or delete buttons

In traditional frontend architectures (React, Angular, vanilla DOM loops), supporting these options leads to messy code:

"If showSearch is true, prepend a search div. Inside the loop, if showSerial is true, unshift a serial TD. At the end of each row, if showActions is true, append action buttons. Repeat across every single component in your codebase."

The consequence is severe: base component templates become polluted with conditional branching logic. Modifying the base table layout risks breaking serial numbering or button alignment.

The Declarative Revelation

In the KeshavSoft Declarative UI Architecture, everything is expressed as structured JSON trees and mathematical transformation instructions. Components are not code functions; they are pure AST specifications.

Rather than baking conditional logic into compilers, json-renderers-run-options introduces a decoupled stage:

1. Clean Base AST
Table blueprint contains only core headers and rows
2. Option Toggles
User passes { showSearch, showSerial, showOptions }
3. Atomic Runner
Dispatches single instructions to enhance the AST

The Evolution: V1 to V2

Version 1: The Data-Role Protocol

The initial version relied on explicit data-role attributes within DOM nodes. The runner recursively scanned the AST to locate nodes whose data-role matched the instruction target (e.g., hasDataRole(base, 'tableRoot')).

Limitation: Every target node had to be explicitly stamped with a rigid data-role tag, limiting flexibility.
Version 2: The JSONPath Revolution (Latest)

In V2, we upgraded target resolution to standard **JSONPath** using jsonpathly. Instructions define dynamic JSONPath destinations:

destinationPath: { jsonPath: "$..*[?(@.attributes['data-role'] == 'headerRow')]" }

The runner validates whether the path matches any node in the AST before execution. If a table doesn't have an actions mount point, the instruction is safely skipped without side effects.

What Everyone Should Understand

Predictable UI: Zero hidden DOM mutations; the resulting AST is pure JSON that can be serialized or inspected anywhere.
Platform Agnostic: Runs in browser environments, Node.js microservices, edge workers, and SSR pipelines.
Zero Code Duplication: The same search and serial instructions work across simple tables, striped tables, and custom cards.
Non-Destructive Safety: Validates targets before dispatching mutations, guaranteeing robust runtime behavior.
